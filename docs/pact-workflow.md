# Pact workflow

Versions: **pact-python 4.1.0** (Pact Rust FFI 0.5.12, Pact specification **V4**). Consumer authoring
uses `pact.Pact`; verification uses `pact.Verifier`. No Ruby, Docker or standalone CLI is required for
either; the Broker is reached over its HTTP API.

```
pytest -m pact_consumer     # mock provider -> pacts/MobileTestPlayground-Mobile-API-MobileTestPlayground-Backend-API.json
pytest -m pact_provider     # replay that contract against the real backend
```

## Consumer provenance — read this first

The contract is a **Python model of the mobile clients' API expectations**, authored in pytest. It is
not generated by the Android or iOS networking code and does **not** prove either app sends these
requests.

That is not a hedge; it is what the repository shows. The Android app's Retrofit client
(`core/data/src/main/kotlin/com/shoptest/core/data/remote/ShopApi.kt`) points at
`https://api.shoptest.local/`, is served by an in-process OkHttp interceptor, and uses a different
DTO shape (`products`/`totalCount`, camelCase fields) — it never calls this backend. There is no iOS
client in the repository.

Every generated pact file records this in its metadata:

```json
"metadata": { "mobileTestPlayground": { "contractSource": "python-model", "provenance": "..." } }
```

and provider verification attaches each contract's source to the report.

**One consumer, deliberately.** With no evidence that Android and iOS expectations differ, two
consumers would duplicate identical interactions. The name is configurable
(`MTP_PACT_CONSUMER_NAME`, default `MobileTestPlayground-Mobile-API`); split it into
`MobileTestPlayground-Android-API` / `-iOS-API` the day their expectations actually diverge.

**Contracts from the real apps.** When the mobile repositories produce their own pacts, drop them into
`MTP_PACT_EXTERNAL_DIR`: they are verified alongside ours (filtered to this provider) and reported as
`external`. Publishing works the same way (`python -m api_tests.pact.broker publish <files...>`).

## Consumer tests

`tests/contracts/consumer/` — 19 interactions, one per test:

| Feature | Interactions |
|---|---|
| Authentication | sign in (valid), sign in (wrong password → 401), current user |
| Products | first page, search + category filter + sort, detail by reference, unknown product → 404, categories |
| Cart | read, add, set quantity, remove line, apply `WELCOME10`, no token → 401 |
| Wishlist | add, remove (204) |
| Orders | place order (cash on delivery), order history, order detail |

Each interaction declares provider state(s), method, path, query, required headers, request body,
status, response headers where the consumer reads them (`WWW-Authenticate`), and **only the response
fields the client relies on**, with matchers for variable values (UUIDs, tokens, prices, dates).

How a test works (`tests/support/pact_consumer.py`): declare the interaction → start the mock provider
→ call it through the framework's own resource clients → the mock provider fails the test on any
mismatch → only then merge the interaction into the contract file. The previous run's file is deleted
at session start, so a stale or failed interaction can never be published or verified.

### Values that differ per backend: provider-state injection

Product/order UUIDs are generated by PostgreSQL and differ per instance; tokens differ per sign-in;
passwords must not be written into a contract. So requests carry a placeholder example plus a
`ProviderState` generator (`api_tests/pact/matchers.py`):

```json
"path":   { "expression": "/api/v1/cart/items/${productId}", "type": "ProviderState" }
"header": { "Authorization": { "expression": "Bearer ${accessToken}", "type": "ProviderState" } }
"body":   { "$.password": { "expression": "${password}", "type": "ProviderState" } }
```

During verification the state-change server returns `{"productId": ..., "accessToken": ...}` and the
verifier substitutes them before replaying the request. No password, token or card number appears in
any pact file (the order contract pays cash on delivery; checked by grep in the test run).

pact-python's convenience matchers ignore a generator when an example is supplied, so `from_state()`
builds `GenericMatcher` directly; the resulting JSON was confirmed by a real verification run.

## Provider verification

`tests/contracts/provider/test_provider_verification.py`:

1. Requires the backend's `/test-data` endpoints (`ENVIRONMENT=development|testing`) — provider states
   need a resettable, **controlled** instance. Never run this against a shared environment.
2. Starts the state-change server (`api_tests/pact/state_server.py`) on `127.0.0.1:<random port>`.
3. Runs `Verifier(...).add_transport(url=MTP_BASE_URL).state_handler(url, teardown=True, body=True)`
   with sources = local pact files (`MTP_PACT_DIR` + `MTP_PACT_EXTERNAL_DIR`) or the Broker.
4. Attaches redacted verifier output, the per-interaction results JSON, every provider-state change,
   and each contract to Allure; one Allure step per interaction.
5. Fails when the verifier fails, when no contract exists, or when it "passes" with zero interactions.

### Provider states

| State | What it does | Injects |
|---|---|---|
| `customer user_001 exists` | (seeded) | `email`, `password` from configuration |
| `customer user_001 is signed in` | signs in the seeded customer | `accessToken` |
| `the catalogue contains the seeded products` | asserts a non-empty catalogue | — |
| `product product_NNN is available` | asserts visible and in stock | `productId` |
| `product product_NNN does not exist` | asserts 404 | — |
| `the customer's cart is empty` | clears the cart | — |
| `the customer's cart contains product_NNN` (`quantity`) | adds the line | `productId` |
| `coupon WELCOME10 is valid` | (seeded; only generally valid codes accepted) | — |
| `the customer's wishlist is empty` / `contains product_NNN` | asserts / adds | `productId` |
| `the customer has placed an order` | fills the cart and places a COD order | `orderId`, `orderNumber` |

**Isolation:** the first setup of each interaction calls `POST /test-data/reset`; all states of that
interaction share one context (one sign-in, merged values); teardown discards it. No interaction can
see another's data, so verification order does not matter. An unknown or failing state answers 500,
which fails the interaction rather than verifying against the wrong state.

### What a failure looks like

A contract expecting `reference: product_002` for `product_001` fails with:

```
Pact verification failed: 1 of 1 interactions.
  $.reference -> Expected 'product_001' (String) to be equal to 'product_002' (String)
```

(verified by running against a deliberately tampered contract).

## Pact Broker

Optional. Local development needs no Broker. Configure with secrets/env only:

| Variable | Purpose |
|---|---|
| `MTP_PACT_BROKER_URL` | Broker base URL |
| `MTP_PACT_BROKER_TOKEN` *or* `MTP_PACT_BROKER_USERNAME` + `MTP_PACT_BROKER_PASSWORD` | auth (never committed) |
| `MTP_PACT_SOURCE=broker` | verify what the Broker selects instead of local files |
| `MTP_PACT_PUBLISH_RESULTS=true` | publish verification results (needs `MTP_BACKEND_VERSION`) |
| `MTP_BRANCH`, `MTP_BUILD_URL` | branch and build metadata |

```bash
# publish the consumer contract with version and branch
python -m api_tests.pact.broker publish --version "$(git rev-parse HEAD)" --branch "$(git branch --show-current)"

# verify from the Broker and publish results
MTP_PACT_SOURCE=broker MTP_PACT_PUBLISH_RESULTS=true MTP_BACKEND_VERSION=<backend sha> pytest -m pact_provider

# gate a release, and record a deployment after it really happened
python -m api_tests.pact.broker can-i-deploy --pacticipant MobileTestPlayground-Mobile-API --version <sha> --environment production
python -m api_tests.pact.broker record-deployment --pacticipant MobileTestPlayground-Backend-API --version <sha> --environment production
```

Broker-sourced verification uses the recommended selectors — consumer main branch, deployed or
released versions, and a matching branch when `MTP_BRANCH` is set — and includes pending pacts.

Exit codes of the CLI: `0` success/deployable, `1` not deployable, `2` configuration or Broker error.
An unreachable Broker or bad credentials is `2` — never a pass. Publishing contracts is **not**
treated as verification: `can-i-deploy` answers "no" until a provider verification result exists.

### Verified against a real Broker

The whole loop was run against a local `pactfoundation/pact-broker:2.143.0-pactbroker2.121.0`
(`make broker-up`, basic auth):

| Step | Result |
|---|---|
| publish consumer `consumer-sha-0001`, branch `main` | published |
| can-i-deploy consumer → production (before verification) | **not deployable** (exit 1) |
| verify from Broker, publish results as `backend-sha-0001` | 19/19 passed; result `success: true` in the Broker |
| can-i-deploy provider → production | deployable (exit 0) |
| record-deployment provider → production | recorded |
| can-i-deploy consumer → production | **deployable** (exit 0) |
| unknown environment / wrong password | exit 2 |

No hosted Broker (e.g. PactFlow) has been used.
